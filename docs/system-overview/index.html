x-bot backend

A Node.js API that helps X (Twitter) users draft posts with AI, publish or schedule them, and send AI replies to tweets.

1. Design walkthrough

If I had to explain this in one minute. x-bot is one Node.js process that is an Express API, a Socket.io server, and three BullMQ workers at the same time. Users log in with X (OAuth 2.0 with PKCE), and the backend keeps their X tokens so it can post for them. The main feature is a chat that turns rough ideas into tweet drafts: the API saves the prompt, puts a job on a queue, and a worker calls GPT-4.1 through GitHub Models and pushes the answer back over Socket.io. Users can also publish a post now, schedule it for later (a delayed queue job), or give a list of tweet URLs and let the bot reply to each one at random times. Postgres (with pgvector) holds users, conversations, scheduled tweets and chat "memory"; KeyDB holds sessions, refresh tokens, OAuth state and all queues.

1.1 Problem and requirements

Functional requirements verified (from the route files):

  • Sign in with X. GET /auth/authorize, GET /auth/callback, POST /auth/refresh, POST /auth/logout.
  • Assisted tweet drafting (chat). Start a conversation, add prompts, ask for 1 or 3 options (SINGLE / MULTIPLE), refine one answer into a thread of revisions. Routes under /api/chat and /api/conversations.
  • Publish now with up to N images (POST /api/post), and schedule / list / cancel text posts (/api/post/schedule, /api/post/scheduled).
  • Bulk AI replies. POST /api/reply takes tweet URLs and a time window; the bot replies to each tweet at a random time inside the window.
  • Profile. GET /user/profile.

Non-functional requirements inferred:

  • Latency hiding. LLM calls take seconds, so chat answers are asynchronous (queue + Socket.io) and the HTTP call returns at once.
  • Reliability for scheduled posts. Retries (3 attempts, exponential backoff from 2 s) and a final FAILED status.
  • "Human-like" timing. Replies are spread at random over up to 6 hours (src/shared/utils/time-randomizer.ts).
  • Security. Short JWT access tokens (15 min), refresh tokens stored only as SHA-256 hashes, PKCE for OAuth.
  • Low cost. GitHub Models as the LLM provider suggests a free or cheap tier is the target.

1.2 Scale and constraints

Scale is not documented. The code shows a small, single-instance design verified:

  • Worker concurrency: chat 5, schedule-post 1, tweet-reply 1 (chat.queue.ts:133, post.queue.ts:351, tweet-reply.queue.ts:594).
  • Chat context: the last 10 messages plus the top 5 memory rows by vector distance.
  • Pagination: keyset for chat turns; in-memory slicing for the conversation list.
  • No API rate limiting, no horizontal scaling setup (no Socket.io Redis adapter), one Postgres pool with default size.

1.3 High-level design

The browser client talks to one Express app over HTTPS with a Bearer JWT. The same HTTP server hosts Socket.io for push events. Slow or deferred work goes onto three BullMQ queues stored in KeyDB; workers in the same process consume them. Workers call two external APIs: the X API (through the official @xdevplatform/xdk SDK) and GitHub Models (through the Vercel AI SDK with an OpenAI-compatible adapter). Postgres is the source of truth for users, X tokens, tweets and chat; KeyDB holds short-lived auth state and the queues.

1.4 One request end to end

The most important action is "send a chat prompt". See the chat sequence diagram. In short:

  1. Sync. POST /api/chat/:id/prompt → authMiddleware verifies the JWT locally (no DB call).
  2. Sync. chat.service.addMessageToConversation checks ownership, inserts a MessageGroup (a turn) and the user Message, reads the last 10 messages (3 to 4 SQL round trips, no transaction).
  3. Sync. chatQueue.add writes the job to KeyDB. The client gets 201 with the turn, without options.
  4. Async. The worker emits message:typing, embeds the prompt (external call 1), runs a pgvector query, calls GPT-4.1 (external call 2), inserts 1 or 3 assistant messages and emits message:received for each.
  5. Async, fire-and-forget. The worker embeds each option and the prompt and writes them to Memory (external calls 3 to 6).

Almost all latency and failure risk of a chat turn comes from GitHub Models. The HTTP part depends only on Postgres and KeyDB.

1.5 Data model and ownership

Postgres is the source of truth for everything durable. KeyDB holds copies and short-lived state. The one important copy is the X access/refresh token pair: it lives in both XAccount (Postgres) and session:<sessionID> (KeyDB), and the two copies are refreshed by different code paths that do not sync. See Data and token lineage.

1.6 The external world

The system depends on four outside systems at runtime: the X API, GitHub Models, a managed Postgres with pgvector, and a managed Redis-protocol store (KeyDB/Valkey). One browser client (at CLIENT_URL) is the only consumer. AWS S3 code exists but nothing calls it. See External world.

1.7 Coupling

This is a modular monolith: features live in separate folders, but they share one database schema module, one KeyDB client, and in-process singletons. The tightest hidden link is between tweet-reply and auth: they share the KeyDB key format session:<id> and a direct import of xTokenRefresh. The chat worker is tied to the HTTP process because it emits through the in-process SocketService singleton. See Coupling.

1.8 Failure modes (summary)

  • KeyDB down: login, token refresh, all queues and the express-session store fail. Chat prompts leave an empty turn in Postgres because the DB writes happen before queue.add.
  • GitHub Models slow or down: chat jobs retry up to 3 × 4 times (BullMQ × AI SDK); the client gets a message:error on each failed attempt.
  • X API down: publish-now returns 500; scheduled posts retry then become FAILED; bulk replies are lost without retry.
  • No explicit timeouts exist on X or LLM calls verified (none in code; SDK defaults apply).

1.9 Bottlenecks and scaling

The first limit will be the GitHub Models rate limit inferred: each chat turn makes 1 chat call and 2 to 5 embedding calls. Next is the single process: you cannot add a second instance without a Socket.io Redis adapter, because workers emit to sockets that may live on another instance. First change: move embedding writes to one batched call and add the Socket.io Redis adapter; both are small.

1.10 Trade-offs and 1.11 weak spots

See Trade-offs and Risks. The most serious weak spots are: logout never revokes refresh tokens, the bulk-reply route has no JWT check and likely never finds a session, X access tokens are printed to the log, and deleting a used conversation likely fails because of the Memory foreign key.

3. Components

HTTP server and bootstrap

Builds the Express app (logging, cookies, JSON, CORS for one origin, express-session in KeyDB), mounts routers, starts Socket.io and all three workers, and handles shutdown. verified

Files and entry points
  • src/server.ts — process entry, workers, signals
  • src/app.ts — middleware order and route mounts
  • src/shared/middleware/* — morgan→pino request log, global error handler

auth

Sign in with X using OAuth 2.0 + PKCE. Upserts User (the user id is the X user id) and XAccount. Issues a 15-minute JWT and a 7-day opaque refresh token (hashed in KeyDB, sent as an httpOnly cookie on path /auth/refresh). verified

Files
  • src/features/auth/auth.controller.ts, auth.service.ts, auth.route.ts
  • src/shared/lib/jwt.ts, src/shared/lib/keydb.ts
  • src/shared/middleware/auth.middleware.ts

chat + conversation

Assisted tweet drafting. A turn (MessageGroup) holds one user question and its assistant options. A refinement is a child turn whose parent_message_id points to an assistant message. The worker generates answers and pushes them over Socket.io. verified

Files
  • src/features/chat/chat.service.ts — DB writes, keyset pagination, recursive CTE for threads
  • src/features/chat/chat.queue.ts — chat-response queue and worker (concurrency 5)
  • src/features/chat/chat.turns.ts — pure helpers (tested)
  • src/features/conversation/* — CRUD on Conversation

post

Publish now (text + images, uploaded in memory with multer, sent to X as base64) and schedule text posts. Scheduling inserts a Tweet row and a delayed BullMQ job with jobId = tweet.id, so cancel can remove the job. verified

Files
  • src/features/post/post.service.ts — dependency-injected for tests
  • src/features/post/post.queue.ts — schedule-post worker (concurrency 1), marks SENT / FAILED
  • src/features/post/post.validation.ts — Joi + multer image filter

tweet-reply

Takes tweet URLs and a time window, spreads jobs at random delays, then for each: reads the tweet (app bearer token), generates a short Web3-style reply with GPT-4.1, and posts it as a reply with the user's token from the KeyDB session. verified

Files
  • src/features/tweet-reply/tweet-reply.service.ts, tweet-reply.queue.ts
  • src/shared/utils/time-randomizer.ts, time-parser.ts
  • src/shared/const.ts — INSTRUCTIONS system prompt

x-account

Stores and returns a user's X access token. getUserAccessToken refreshes it when it expires in under 30 minutes and saves the new pair. Used by publish and the schedule worker. verified

Files
  • src/features/x-account/x-account.service.ts

AIService

Wraps the Vercel AI SDK with an OpenAI-compatible provider pointed at BASE_URL (GitHub Models). Chat model gpt-4.1, embeddings openai/text-embedding-3-small (1536 dims). Also does RAG: top-5 Memory rows by cosine distance per conversation. verified

Files
  • src/shared/services/ai.service.ts
  • src/shared/prompt-templates.ts (CHAT_SYSTEM_PROMPT; TWEET_PROMPTS is unused)

XService + x-client.factory

The adapter for the X API. It creates xdk clients (OAuth2 user token or app bearer token), uploads media, creates posts and replies, reads a post by id, and reads users/me. The OAuth2 helper is a module singleton. verified

Files
  • src/shared/services/x.service.ts
  • src/shared/services/x-client.factory.ts — scopes: tweet.read/write, users.read, users.email, media.write, offline.access

SocketService

Singleton Socket.io server. Checks the JWT on handshake, then lets a socket join conversation:<id> rooms. Workers emit message:typing, message:received, message:refined, message:error. verified

Files
  • src/shared/services/socket.service.ts

Data access

Drizzle ORM over a pg pool, one schema file for all tables. Migrations are hand-written SQL applied by scripts/run-migration.ts, tracked in a _migrations table. verified

Files
  • src/shared/db/index.ts, schema.ts
  • drizzle/migrations/000*.sql
  • src/shared/utils/keydb-client.ts, src/shared/lib/keydb-url.ts

sequenceDiagram

  participant K as KeyDB BullMQ
  participant W as schedule-post worker

Notice the order "post to X, then update DB": if the DB update fails, the retry posts the tweet a second time.

4.4 Bulk AI replies (short)

  1. Sync. POST /api/reply (no JWT check). Joi parses maximumTime such as "2h" to milliseconds.
  2. Sync. getSessionTokens(req.sessionID) reads session:<sessionID> from KeyDB; it throws if nothing is there.
  3. Sync. One delayed job per URL with random cumulative delays inside the window.
  4. Async. Worker re-reads the session tokens, gets the tweet text with the app bearer token, generates a reply, posts it with in_reply_to_tweet_id. Errors are caught and returned as a result, so BullMQ does not retry.

Judgment

  • Hot spots (fan-in). src/shared/db/schema.ts + db (used by 7 modules), keydbClient (sessions, OAuth state, refresh tokens, X tokens, all queues), XService (auth, x-account, post, tweet-reply). verified
  • Fan-out. chat.queue.ts worker depends on Postgres, KeyDB, GitHub Models and Socket.io at once. verified
  • Cycles. None found between modules. chat.service → chat.queue is one-way. verified by reading imports.
  • Modular or not? A modular monolith with leaks. Features are separated by folder, but tweet-reply reaches into auth's KeyDB key format, two places hand-write raw SQL against table names (chat.service.ts:524, ai.service.ts:850), and the chat worker cannot run in a separate process without changing how it emits events.
  • Co-change evidence. auth.service.ts and auth.controller.ts are the most-changed source files (21 and 18 commits). The XDK migration (2026-07-22) touched auth, post, tweet-reply and x-account in one series, which shows they all share the XService contract.

Notice the two weak crossings: /api/reply and Socket.io room joins.

  • Checked. JWT on all /api/chat, /api/conversations, /api/post, /user routes; ownership checks in services (requireConversation, findOwned); PKCE + state for OAuth; image MIME filter. verified
  • Not checked. /api/reply has no authMiddleware (tweet-reply.route.ts:7). conversation:join lets any authenticated socket join any room (socket.service.ts:44). No rate limiting. No upload size limit on multer. take query param is unbounded. verified

Compliance, ownership and vendor risk

  • Data leaving your control. User prompts and drafts go to GitHub Models (Microsoft/GitHub). Tweets, images and replies go to X. Where those vendors process data is not stated in the repo. inferred
  • Platform policy risk. The bulk reply feature posts AI-generated replies at randomized times. X's automation rules restrict automated replies; this can put user accounts or the X app at risk. Question for the owner. inferred
  • Lock-in. X is not replaceable (the product is X-specific). The LLM vendor is easy to swap. The Redis store is already swappable.

Bottlenecks, in the order they will hit

  1. LLM rate limits. Each chat turn = 1 chat call + 2 (SINGLE) or 4 (MULTIPLE) embedding calls + 1 more for retrieval. Fix: batch embeddings with embedMany, or skip storing assistant options. inferred
  2. Memory query. No vector index and probably no index on Memory.conversation_id, so retrieval scans rows. Fine now; add an index when memory grows. inferred (no index in migrations or schema)
  3. Conversation list. getConversations loads all of a user's conversations, then slices in memory (conversation.service.ts:28). verified
  4. Single instance. A second instance needs the Socket.io Redis adapter; otherwise workers emit to the wrong process.
  5. X API caps. Post and read limits per tier will cap bulk replies before compute does. inferred

8. Trade-offs

Async chat (queue + Socket.io) instead of a streamed HTTP response

Gain: the request returns fast, jobs survive restarts and retry.

Cost: two channels to keep in sync, a join-before-emit race, no token streaming, and the worker is tied to the HTTP process.

Evidence: commit 631f171 added Socket.io; chat queue design in chat.queue.ts. Reasoning is inferred.

One process for API and workers

Gain: one deploy, one config, simple local dev.

Cost: a slow LLM job and HTTP traffic share one event loop; you cannot scale them separately.

Evidence: src/server.ts starts all workers. verified

pgvector in Postgres instead of a vector database

Gain: one store, joins with chat data, no extra vendor.

Cost: vector type is a custom Drizzle type; queries use raw SQL; no ANN index yet.

Evidence: schema.ts custom vector(1536); commit 552b403. verified

Prisma → Drizzle, with hand-written SQL migrations

Gain: lighter runtime, full control over destructive steps (migration 0000 deletes legacy rows on purpose).

Cost: the drizzle-kit journal (0000_add-profile-imgs) does not match the SQL files, and the base tables come from an old Prisma 0_init migration that is no longer in the tree, so a fresh database cannot be built from this repo alone.

Evidence: commits cffa306 (2026-06-27) to 19c3ae8 (2026-09-10). verified

Raw fetch → official X SDK (xdk)

Gain: less code (auth service lost 96 lines), PKCE and refresh handled by the SDK.

Cost: dependency on a 0.x SDK; some fields are read through as any (confirmed_email, mediaType).

Evidence: PR.md, commits 2026-07-22. verified

Stateless JWT + server-side refresh tokens

Gain: no DB call per request; refresh tokens can be revoked per user.

Cost: profile data in the JWT can be 15 minutes stale; revocation only works if logout works (it does not today, see Risks).

Evidence: commit 917fa68 removed email/password auth. verified

11. Conventions

  • Feature folders: <feature>.route / controller / service / validation / queue / types .ts. Services have no Express types (except post.service, which takes Express.Multer.File).
  • ESM with .js import suffixes; relative imports only; strict TypeScript with unused-variable checks.
  • Controllers use try/catch + next(error); success responses go through sendResponse(res, status, message, data, pagination?); errors use classes in src/shared/lib/errors.ts. Exceptions: auth.controller and tweet-reply.controller have no try/catch (Express 5 forwards async errors, so this still works).
  • Joi for validation; stripUnknown: true. Two feature files define their own validateBody.
  • DB columns are snake_case (one exception: Tweet.dateScheduled). Table names are PascalCase.
  • Logging: AGENTS.md says pino, but most code uses console.*.
  • Docs drift: AGENTS.md still describes Prisma and Vitest; API.md still mentions refinement by parent_id, which migration 0000 removed. verified
